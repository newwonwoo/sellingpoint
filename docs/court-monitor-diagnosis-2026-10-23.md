## 필요한 개선

외부 장애를 고친다고 주장하지 않는다. 아래는 점검기에서 확인된 진단·판정의 결함만 보완한다.

1. 정기점검에서 같은 러너·목적지로 최대 3회, 5초/10초 간격 재시도한다. 연결 단계 제한은 8초에서 12초로 소폭 늘린다. 브라우저는 기존 30초를 유지한다. 일반 사건조회 워크플로에는 재시도 횟수를 추가하지 않는다(기본 1회).
2. DNS/TCP/TLS/HTTP 실패의 오류 종류·errno·소요시간과 각 시도 결과를 저장한다. 최종 NETWORK_ERROR일 때 공개 GitHub HTTPS 대조 연결을 1회 확인한다. 대조 결과는 목적지 경로 문제와 공통 경로 문제의 관측을 나누며 원인을 확정하지 않는다.
3. 401/403은 ACCESS_DENIED, 429는 RATE_LIMITED로 분류하고 브라우저 추가 요청과 재시도를 중단한다. 서버 Retry-After를 짧은 재시도로 무시하지 않는다. 5xx, 브라우저 실행환경 오류, 화면 초기화 미확인을 구분한다.
4. 검색화면 식별 근거가 부족하거나 리소스 연결 오류가 있는 미완성 화면을 구조 변경으로 판정하지 않는다. 정상 화면의 실제 필수요소 누락은 기존 구조 변경 분류를 유지한다.
5. 사전검사 후 조회가 실패했다는 이유만으로 API_OR_RESULT_CHANGED를 부여하던 로직을 제거한다. 접속·시간초과·캡차·검증 사건 불일치는 unavailable로 두고, 정상 HTTP/결과 화면에서 확인된 명시적인 계약 변경 증거만 structure_changed로 보고한다. 조회 단계의 FORM/CAPTCHA 이벤트에는 리소스 로딩 증거가 없으므로 판정을 보류하고 사전 진단의 확인된 화면 변경과 구분한다. API 전송/HTTP 오류는 구조 이벤트보다 우선한다. 정상적인 화면 폴백 결과는 기존처럼 healthy다.
6. 보고서를 독립 모듈로 분리하고 Actions 요약과 원본 진단 아티팩트로 남긴다. unavailable도 Actions 실패로 표시하므로 장애가 성공으로 숨겨지지 않는다.

`search.py`, API 요청 형식, 캡차 처리, 데이터 파싱과 출력 스키마는 수정하지 않는다. 진단 브라우저의 자동화 지문 은폐 플래그를 제거했다. IP/러너/프록시 교체나 보안 제한 우회는 추가하지 않는다.

## 검증

회귀 테스트는 모의 전송과 로컬 HTTP 서버를 사용한다. 실제 법원 접속이나 사건검색을 추가로 실행하지 않는다.

- TCP 시간초과 후 복구, 지속 실패의 횟수·대기시간 상한, 대조 연결 결과와 원인 미확정 표시.
- HTTP 403/429 중단, 503 및 Retry-After, 브라우저 실행환경 오류.
- 실제 Chromium에서 정상 화면, 입력폼/캡차 변경, HTTP 403/429/503, 점검 화면, JS 리소스 실패 구분.
- 사전 진단 실패, 조회 결과 누락·시간초과·네트워크 오류·캡차 실패·사건 불일치가 구조 변경으로 바뀌지 않는지 확인.
- 기존 셀렉터 의미 검증, 직접 API 계약, 조회 스케줄러, 캡차 고속 경로 회귀검증.

새 회귀검증 워크플로는 실제 법원 사이트에 요청하지 않으며 브랜치/PR에서 테스트를 실행한다. 본문에 기록한 실서비스 정상 결과는 수정 전 최신 정기점검의 증거다. 변경 후 실서비스 정상화를 입증하는 실행과 혼동하면 안 된다.
